# 상담 지원 사이트(udjcs.ggm.kr) 배포·운영 안내

우리동네 직업계고를 상담 직원이 대신 들여다보는 화면이다.
본 사이트와 **같은 백엔드(8000), 같은 DB** 를 쓰고, 화면만 따로 있다.

```
udjschool.ggm.kr  ← 고객용 (frontend)
diary.ggm.kr      ← 기록해 (frontend-journal, 백엔드 8100)
udjcs.ggm.kr      ← 상담 지원 (frontend-cs, 백엔드 8000 공유)  ← 새로 추가
```

---

## 1. 처음 한 번만 하는 일

### DNS

`udjcs.ggm.kr` A 레코드를 `49.50.133.46` 으로 추가한다. 전파를 기다린 뒤 다음으로 넘어간다.

```bash
dig +short udjcs.ggm.kr        # 49.50.133.46 이 나와야 한다
```

### nginx

```bash
sudo cp ~/hs-portal/deploy/nginx-cs.conf /etc/nginx/sites-available/udjcs
sudo ln -s /etc/nginx/sites-available/udjcs /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
sudo certbot --nginx -d udjcs.ggm.kr
```

**확인** — `proxy_pass` 가 **8000** 인지 본다. 기록해 설정을 복사해 쓰다 8100 으로 들어가는 사고가 전에 있었다.

```bash
sudo nginx -T 2>/dev/null | grep -A2 "server_name udjcs" | grep proxy_pass
```

### .env

`backend/.env` 의 `ALLOWED_ORIGINS` 에 주소를 추가한다.

```
ALLOWED_ORIGINS=https://udjschool.ggm.kr,https://diary.ggm.kr,https://udjcs.ggm.kr
```

값 뒤에 `#주석`을 붙이면 안 된다. systemd 가 주석까지 값으로 읽는다.

```bash
sudo systemctl restart udt-backend
```

### 첫 관리자 접속

대표님 관리자 계정으로 `https://udjcs.ggm.kr` 에 로그인한다.
관리자는 기기 승인 없이 들어간다(승인하는 사람이 못 들어오면 안 되므로).

---

## 2. 배포

본 사이트와 같은 방식이다. `frontend-cs` 빌드가 하나 늘었을 뿐이다.

```bash
cd ~
cp ~/hs-portal/backend/.env ~/env.backup
unzip -o hs-portal.zip
cp ~/env.backup ~/hs-portal/backend/.env

cd ~/hs-portal/frontend     && npm install && npm run build
cd ~/hs-portal/frontend-cs  && npm install && npm run build      # ← 새로 추가
sudo systemctl restart udt-backend
```

`udj_tool.py` 를 쓰신다면 배포 단계에 `frontend-cs` 빌드를 한 줄 넣어야 한다.
안 넣으면 백엔드만 갱신되고 상담 화면은 예전 것이 남는다.

DB 는 따로 손댈 것이 없다. 서버가 뜰 때 `cs_devices` 테이블과 `cs` 권한 값이 자동으로 만들어진다.

## 3. 접근 제한이 동작하는 방식

로그인은 세 단계를 지난다.

1. **비밀번호 확인** — 틀리면 여기서 끝. 기기 요청도 안 쌓인다
2. **사무실 IP 인가** — 등록된 IP·대역이면 그대로 통과
3. **승인된 기기인가** — 그 밖에서는 관리자가 승인한 기기여야 한다

**요청마다 다시 검사한다.** 승인을 끊으면 이미 로그인해 있던 사람도 다음 클릭에서 막힌다.

### 새 상담원을 들일 때

1. 관리자로 접속 → **기기·상담원 → 상담원 → 상담원 추가**
2. 이메일과 첫 비밀번호를 직접 전달한다(메일로 보내지 않는다)
3. 상담원이 로그인하면 화면에 **6자리 코드**가 뜬다
4. 그 코드를 전화나 대면으로 확인한 뒤 **기기 승인** 탭에서 승인한다

코드를 확인하는 이유는, 목록에 뜬 것이 정말 그 사람 기기인지 알 방법이 그것뿐이기 때문이다.

### 사무실 IP 등록

**기기·상담원 → 사무실 IP** 에서 지금 접속한 IP 가 화면에 보인다. 사무실에서 열었다면 그 값을 넣으면 된다.

다만 **회선이 고정 IP 가 아니면 주소가 바뀐다.** 어느 날 갑자기 전원이 기기 승인 대상이 되는 일이 생길 수 있으니, 이 경우 IP 를 비워두고 기기 승인만 쓰는 편이 오히려 안정적이다.

### 노트북을 잃어버렸을 때

**기기 승인** 탭에서 해당 기기를 **중지**한다. 즉시 막힌다.
계정 자체를 막아야 하면 **상담원** 탭에서 **사용 중지** — 이때 그 사람의 기기가 전부 함께 끊긴다.

## 4. 상담원이 할 수 있는 일

| | |
|---|---|
| **볼 수 있다** | 회원(연락처 마스킹), 학교, 문의, 후기, 학교 주문, 개인 구독, 재학생 인증 |
| **할 수 있다** | 문의 답변, 비밀번호 재설정 코드 발송, 학교 정보 수정, 후기 숨김·복구, 재학생 인증 승인·반려, 입금 확인 |
| **할 수 없다** | 계정·학교 삭제, 무상 플랜 지급, **주문 최종 승인**, 요금·계좌 설정, 공지 등록, 감사 로그 열람, 상담원 관리, 기사 크롤링 |

할 수 없는 일은 **화면에서 숨긴 것이 아니라 API 자체가 없다.** 주소를 직접 쳐도 안 된다.

### 개인정보 취급

- 목록에서는 이메일·연락처가 언제나 가려진다
- 상세에서 **원본 보기**를 누르면 열리고, **누가 언제 누구 것을 열었는지 기록된다**
- 비밀번호는 상담원이 정해줄 수 없다. 본인 메일로 6자리 코드가 갈 뿐이다
- 기록은 1년 보관되며 **관리자만** 볼 수 있다(기기·상담원 → 활동 기록)

### 입금 확인과 최종 승인을 나눈 이유

상담원은 `입금대기 → 입금확인` 까지만 한다. 플랜이 실제로 켜지는 것은 관리자의 최종 승인 시점이다.
돈이 들어온 것을 확인하는 일과 서비스를 여는 일을 나눠 두면, 한 사람의 착오로 유료 기능이 열리지 않는다.

---

## 5. 안 될 때

**로그인 화면에서 계속 "기기 승인이 필요합니다"**
→ 관리자가 승인했는지 확인한다. 승인했는데도 그렇다면 상담원이 **다른 브라우저나 시크릿 창**을 쓰고 있을 가능성이 높다. 기기 토큰은 브라우저별로 저장되므로 승인받은 그 브라우저에서 열어야 한다.

**사무실인데 기기 승인을 요구한다**
→ 회선 IP 가 바뀐 것이다. 관리자 화면에서 현재 IP 를 다시 확인해 등록한다.

**모두가 사무실 IP 로 통과된다 (또는 아무도 통과 안 된다)**
→ nginx 의 `X-Forwarded-For` 헤더 설정이 빠졌을 가능성이 크다. 이 줄이 없으면 모든 접속이 `127.0.0.1` 로 보인다.

```bash
sudo nginx -T 2>/dev/null | grep -A8 "server_name udjcs" | grep X-Forwarded-For
```

**문의 답변이 발송 실패로 뜬다**
→ 학교가 자체 메일을 등록하지 않았고 포털 SMTP 도 설정되지 않은 경우다. `backend/.env` 의 `SMTP_*` 값을 확인한다. 답변 내용 자체는 저장돼 있으므로 설정을 고친 뒤 다시 보내면 된다.
