# CS 전화상담(콜센터) 설계

우리동네직업계고 상담 사이트(udjcs.ggm.kr)에 **전화 응대**를 얹는다.
이미 있는 CS 콘솔·계정·기기승인·감사로그를 그대로 쓰고, 그 위에 전화 계층만 새로 만든다.

---

## 1. 통신 구조 — 무엇을 우리가 만들고, 무엇을 못 만드는가

```
고객
 │
 ▼
스마텔 010 번호            ← 이동통신망(LG U+ 재판매). 우리가 제어할 수 없다.
 │  착신전환
 ▼
전화 Provider / SIP GW     ← 외부 사업자. 아직 미정. 우리가 만드는 게 아니다.
 │  webhook / SIP 이벤트
 ▼
CS Backend (FastAPI)       ← 여기서부터 우리 코드
 │  DB 이벤트 아웃박스
 ▼
WebSocket /api/cs/ws/calls
 │
 ▼
상담원 브라우저 (WebRTC softphone)
```

**중요한 사실을 먼저 못 박는다.**

- React·FastAPI·WebRTC 만으로는 010 이동전화를 받을 수 없다. 반드시 PSTN↔SIP
  게이트웨이를 가진 **외부 전화 사업자**가 있어야 한다.
- 스마텔 착신전환이 임의의 SIP URI 로 갈 수 있다는 보장은 없다. 보통은
  **국내 유선번호(070/1544 등)** 로만 전환된다. 그래서 실제 연동 순서는
  ① 사업자에게서 DID(070 등) 번호를 받고 → ② 스마텔 착신전환 대상을 그 번호로
  잡고 → ③ 그 번호로 들어온 콜을 사업자가 우리 웹훅/SIP 로 넘기는 방식이다.
  이건 사업자 선정 후 **실제 통화로 검증해야 확정**된다.
- 그때까지 이 저장소의 전화 계층은 `MockPhoneProvider` 로 돈다. Mock 은
  분배·상태·기록·화면을 전부 실제와 똑같이 돌리지만 **음성은 흐르지 않는다.**

## 2. 계층 분리

| 계층 | 위치 | 사업자 의존 |
|---|---|---|
| 전화망 어댑터 | `backend/app/phone/` | **여기만** 의존한다 |
| 순차분배·큐 엔진 | `backend/app/callcenter/engine.py` | 없음 |
| CS API·WebSocket | `backend/app/callcenter/api.py` | 없음 |
| 상담원 화면 | `frontend-cs/src/pages/Calls.jsx` 등 | 없음 |

`PhoneProvider` 인터페이스(`phone/base.py`)만 지키면 사업자를 바꿔도
엔진·API·화면은 손대지 않는다.

```
PhoneProvider (ABC)
 ├── MockPhoneProvider   개발·훈련용. 가짜 전화를 만든다.
 └── SipPhoneProvider    실제 SIP/웹훅 사업자용 골격. 사업자 확정 후 채운다.
```

메서드: `initialize / receive_call / answer_call / reject_call / hangup_call /
transfer_call / get_call_status / get_active_calls / make_call / set_webhook`

## 3. 순차분배

```
콜 인입
 └─ 활성 상담원 목록을 ring_order 순으로 정렬
    └─ step 0 상담원 호출 → RING_TIMEOUT(기본 20초) 대기
       ├─ 받음  → ANSWERED. 상담원 BUSY.
       ├─ 거절  → 즉시 다음 step
       └─ 무응답 → 다음 step
    └─ 마지막 step 까지 실패 → QUEUED(대기열)
       └─ 누군가 AVAILABLE 이 되면 큐 머리부터 다시 링
```

- 상담원 수·순서는 DB(`cs_counselor_profiles.ring_order`)에서 온다. 하드코딩 없음.
- RING_TIMEOUT·순차분배 사용여부·큐 사용여부는 `settings` 테이블에서 온다.

## 4. 왜 상태를 DB 에 두는가 (운영 워커 3개 문제)

운영은 `gunicorn --workers 3` 이다. 콜 상태를 파이썬 메모리에 두면
**웹훅을 받은 워커와 상담원 WebSocket 이 붙은 워커가 달라서** 화면에 전화가 뜨지 않는다.

그래서:

- 콜의 진행 상태는 `cs_call_sessions` 테이블에 둔다.
- 화면에 보낼 이벤트는 `cs_call_events` **아웃박스 테이블**에 쌓는다.
  WebSocket 은 자기가 마지막으로 보낸 id 이후만 읽어 내보낸다(≈0.7초 간격).
- 링 타임아웃은 각 워커의 배경 티커가 `UPDATE ... WHERE ring_step = :n` 이라는
  낙관적 조건으로 넘긴다. 세 워커가 동시에 깨어도 한 번만 넘어간다.

Redis 없이 워커 3개에서 정확히 동작한다. 대가는 최대 1초 지연이다.

## 5. 데이터 모델 (전부 신규 테이블, 기존 것 건드리지 않음)

| 테이블 | 뜻 |
|---|---|
| `cs_customers` | 상담 고객. 전화번호 정규화 저장 |
| `cs_consultations` | 상담 기록 |
| `cs_call_logs` | 통화 이력(끝난 것 포함) |
| `cs_call_sessions` | 진행 중인 콜의 분배 상태 |
| `cs_call_events` | WebSocket 아웃박스 |
| `cs_counselor_profiles` | 기존 `users` 에 딸리는 상담원 전화 설정 |
| `cs_inquiry_types` | 문의 유형 |

기존 `users` 를 상담원 계정으로 그대로 쓴다. 상담원 테이블을 새로 만들면
계정이 두 벌이 되어 비밀번호·권한·기기승인이 갈라진다.

전화번호는 `01012345678` 형태로 정규화해 저장하고, 화면에는 마스킹해 보여준다.

## 7. WebRTC 의 현재 위치

브라우저 쪽 소프트폰(마이크 권한, 음소거, 통화시간, 종료)은 만들어 두었다.
다만 **음성 경로는 Provider 가 정해져야 완성된다.** Mock 에서는 마이크만 잡고
오디오는 흐르지 않는다. 사업자가 정해지면 `phone/sip.py` 에서 SDP 교환을
붙이고 화면은 그대로 쓴다.

## 7-2. 전화 사업자 고르기 — 계약 전에 확인할 것

### 0단계. 스마텔 확인 — 끝났다 (2026-09-06)

**결과: 스마텔은 착신전환 서비스 자체를 제공하지 않는다.**

그래서 지금 번호를 그대로 둔 채로는 010 으로 온 전화를 PC 로 받을 수 없다.
원래 설계의 전제(스마텔 착신전환)가 성립하지 않으므로 아래 둘 중 하나를 고른다.

**A. 번호이동** — 010 번호를 그대로 들고, 착신전환을 제공하는 통신사로 옮긴다.

원안(010 유지)에 가장 가깝다. 번호는 바뀌지 않고 통신사만 바뀐다.
다만 옮기기 **전에** 그 통신사에 두 가지를 반드시 확인한다.

  1. 착신전환 부가서비스를 제공하는가
  2. **070(또는 우리가 받을 지역번호)으로도 전환되는가**

1번은 되는데 2번이 안 되는 통신사가 있다. 옮기고 나서 알면 늦는다.

**B. 대표번호를 새로 안내** — 070·지역번호·1544 를 대표번호로 홈페이지와
명함에 올리고, 010 은 지금처럼 휴대폰으로 받는다.

위험이 없고 지금 당장 할 수 있다. 대신 010 을 이미 아는 사람은 계속 휴대폰으로
건다. 시간이 지나며 대표번호 쪽으로 옮겨가기를 기대하는 방식이다.

### 순서를 틀리지 말 것

**어느 쪽을 고르든 070(또는 지역번호) 회선이 먼저 있어야 한다.**
번호이동을 먼저 해봐야 착신전환을 걸 대상 번호가 없으면 아무 의미가 없다.
게다가 업체가 어떤 번호(070 인지 지역번호인지)를 주느냐에 따라 통신사에
물어볼 질문이 달라진다.

```
① 업체 계약 → 번호 확보
② (A안이면) 그 번호로 착신전환 되는 통신사 확인 → 번호이동 → 착신전환 설정
③ .env 채우고 sip.py 구현
```

CS 시스템 자체는 ①만 끝나면 실제 통화가 된다. ②는 010 을 살리기 위한 별도 과제다.

### 업체에 물어볼 것

| # | 질문 | 왜 중요한가 |
|---|---|---|
| 1 | 010 착신전환을 받을 DID(070 등) 번호를 주는가 | 이게 없으면 시작이 안 된다 |
| 2 | 인바운드 콜을 우리 서버 **웹훅(HTTPS)** 으로 알려주는가 | SIP 트렁크만 주면 우리가 SIP 스택을 직접 붙여야 해서 일이 몇 배가 된다 |
| 3 | **브라우저에서 통화를 받을 수 있는가 (WebRTC SDK/게이트웨이 제공)** | **갈림길.** 없으면 상담원이 PC 로 못 받고 IP전화기·전용앱을 따로 써야 한다 |
| 4 | 여러 상담원에게 순서대로 울리는 것을 **우리가 제어**할 수 있는가 | 업체 ACD 에 맡기면 순차분배 규칙이 두 벌이 되어 관리자 화면과 실제가 어긋난다 |
| 5 | 발신 시 표시번호로 우리 번호를 등록할 수 있는가 | 발신번호 사전등록. 변작은 불법이라 등록된 번호만 쓸 수 있다 |
| 6 | 동시통화 채널을 몇 개 주는가 | 상담원 3명이면 최소 3채널. 채널이 모자라면 통화 중 신호가 난다 |
| 7 | 녹취를 제공하는가, 파일은 어디에 얼마나 보관되는가 | 26장. 켤지 말지는 나중에 정해도 되지만 조건은 미리 안다 |
| 8 | 요금 구조 (회선료 / 분당 통화료 / 채널 추가비) | |

3번이 안 되는 업체를 고르면, 지금 만든 상담원 화면의 전화 부분은 못 쓴다.
고객정보·상담기록·통계는 그대로 쓸 수 있지만 전화기가 따로 놓이게 된다.

### 계약한 뒤 우리가 할 일

받아온 값 네 개를 서버 `.env` 에 넣는다. 실제 번호와 키는 코드에 넣지 않는다.

```
PHONE_PROVIDER=sip
PHONE_API_BASE=...
PHONE_API_KEY=...
PHONE_WEBHOOK_SECRET=...
PHONE_DID_NUMBER=...
```

그다음 `backend/app/phone/sip.py` 세 곳만 그 업체에 맞게 채운다.

1. `verify_webhook` — 그 업체의 서명 방식
2. `parse_webhook` — 그 업체의 이벤트 이름 → `CallEventType`
3. `answer_call` / `reject_call` / `hangup_call` / `ring_agent` / `make_call` — 그 업체의 REST 호출

엔진(`callcenter/engine.py`)·API·상담원 화면은 손대지 않는다. 그러라고 계층을 나눴다.

사업자등록번호는 계약 서류에만 쓴다. CS 시스템은 그 값을 알 필요가 없고,
코드나 `.env` 에 넣지 않는다.

## 7-5. ClawOps 연결 (2026-09-06 070 번호 발급 완료)

070 회선을 ClawOps(팀러너스)에서 받았다. 번호는 코드에 적지 않고 `.env` 의
`PHONE_DID_NUMBER` 에만 둔다.

### ClawOps 는 명령을 받지 않는다. 되물어본다

Twilio 와 같은 방식이다. 전화가 올 때마다 우리에게 묻고, 우리가 XML(VoiceML)로
답한 대로 움직인다. **이 구조가 우리 순차분배 엔진과 정확히 맞물린다.**

```
전화 도착
  ClawOps → POST /api/cs/phone/voice/incoming
  우리    → <Dial timeout="20" action="…/after-dial"><Number>김상담</Number></Dial>

20초 무응답  (시간은 ClawOps 가 센다)
  ClawOps → POST …/after-dial   DialCallStatus=no-answer
  우리    → 엔진에게 다음 사람을 묻고 <Dial>…이상담…</Dial>

아무도 못 받음
  우리    → <Say>기다려 주세요</Say><Pause/><Redirect>…/queue</Redirect>
            대기열에서 10초마다 다시 물어본다(최대 3분)

받음
  ClawOps → POST …/after-dial   DialCallStatus=completed
  우리    → <Hangup/>
```

**20초를 세는 일은 사업자가, 누구를 부를지는 우리가.** 그래서 Provider 가
`external_ring_timeout` 을 알리면 엔진은 `ring_deadline` 을 비워 둔다. 안 그러면
배경 ticker 와 ClawOps 가 같은 통화를 각각 넘겨 한 번에 두 사람을 건너뛴다.

### 상담원을 무엇으로 부르는가 — 갈림길

전화 설정 화면에서 고른다.

| 모드 | 무엇으로 | 조건 |
|---|---|---|
| `number` | 상담원 **휴대폰** (`<Dial><Number>`) | 없음. 오늘 당장 된다 |
| `sip` | 상담원 **PC 브라우저** (`<Dial><Sip>`) | **SIP 트렁크 부가서비스** 필요 |

`number` 모드면 통화는 휴대폰으로 하고 고객정보·상담기록·통계·순차분배는 화면에서
그대로 쓴다. 원안(PC 로 통화)의 절반이지만 나머지 절반이 전부 살아 있다.

### 브라우저로 받기 (sip 모드) — 2026-09-06 ClawOps 확인 완료

가능하다. **SIP 트렁크 연결 부가서비스**를 계정 소유자 권한으로 켜야 한다
(platform.claw-ops.com/addons). 켜지 않으면 등록 자체가 차단된다.

동작 순서

```
① 상담원이 /calls 를 연다
   브라우저 → POST /api/cs/phone/webrtc-token
   서버    → ClawOps 에서 단기 토큰을 받아 브라우저에 넘기고,
             그 토큰의 SIP 주소를 이 상담원 앞으로 기록한다
② 브라우저가 JsSIP 로 register:true 등록
③ 전화가 오면 우리 웹훅이 그 주소로 <Dial><Sip>sip:ephem_…@…</Sip></Dial>
④ 브라우저에 INVITE 도착 → 화면의 [받기] 를 누르면 session.answer()
```

**까다로운 지점은 토큰 수명이다.** 5~7분이면 만료되고, 만료되면 등록이 풀려
전화가 오지 않는다. 게다가 **다시 받을 때마다 SIP 주소가 바뀐다.** 그래서

- 브라우저가 수명의 60% 지점에서 미리 다시 받아 재등록한다
- **통화 중이면 재등록을 미룬다.** 통화 중에 재등록하면 그 통화가 끊긴다
- 주소는 **서버가 발급하면서 직접 기록한다.** 브라우저가 "제 주소는 이겁니다"
  하고 신고하게 두면 남의 전화를 자기에게 돌리도록 거짓말할 수 있다
- 만료된 주소를 가진 상담원은 분배에서 건너뛴다. 아무도 없는 곳으로 돌리면
  고객이 20초를 헛되이 기다린다

사업자 API 키는 브라우저로 내려가지 않는다. 서버만 알고, 브라우저는 자기
계정용 단기 자격증명만 받는다.

필요한 설정 하나가 더 있다.

```
PHONE_SIP_CREDENTIAL_ID=<부가서비스를 켠 뒤 만든 SIP 자격증명 ID>
```

이 값이 있어야 `webrtc_audio` 가 켜지고, 화면이 브라우저 전화기를 시작한다.
없으면 조용히 휴대폰 모드로 돈다.

### 서명 검증

`X-Signature` 헤더, HMAC-SHA256, **Base64**.
서명 대상은 `웹훅 URL + (키를 사전순 정렬한 key+value 이어붙임)`.

URL 이 한 글자만 달라도 어긋난다. `PHONE_VOICE_BASE` 는 대시보드에 등록한
주소와 **완전히 같은 문자열**이어야 한다.

### 붙이는 순서

```
1) .env 채우기   PHONE_PROVIDER=clawops / PHONE_API_KEY / PHONE_ACCOUNT_ID
                 PHONE_WEBHOOK_SECRET / PHONE_DID_NUMBER / PHONE_VOICE_BASE
2) 서버 재시작   값이 하나라도 비면 서버가 뜨지 않는다(일부러 그렇게 두었다)
3) 전화 설정 화면에서 상담원 휴대폰 번호를 채운다  ← 비면 그 사람은 건너뛴다
4) ClawOps 대시보드 > 전화번호 > 인바운드 라우팅 > WEBHOOK 에
   https://udjcs.ggm.kr/api/cs/phone/voice/incoming
5) 그 번호로 직접 전화를 걸어 본다
```

5번을 하기 전에는 **된다고 말하지 않는다.** 검사 27개가 통과했지만 그건 우리가
만든 가짜 웹훅에 대한 것이고, 실제 통화와는 다르다.

## 7-3. 홈페이지 문의가 상담으로 들어오는 방법

문의(Inquiry)에 **답하는 것은 여전히 학교다.** 그 흐름은 건드리지 않았다.
다만 상담원이 "오늘 우리한테 들어온 일"을 전화와 홈페이지 두 화면으로 나눠
보면, 놓치는 건은 반드시 그 사이에서 생긴다. 그래서 문의가 접수되는 순간
상담 목록에 읽기용 사본을 하나 만든다.

```
방문자 → POST /api/schools/{id}/inquiries   (기존 그대로)
            ├── Inquiry 저장          학교가 답변할 원본
            └── CsConsultation 생성   상담원이 보는 사본 (채널 HOMEPAGE)
                    └── 전화번호가 있으면 고객으로도 등록된다
```

지금 UDJ 백엔드와 CS 백엔드는 **같은 프로세스**다. 그래서 HTTP 를 거치지 않고
바로 함수를 부른다(`callcenter/intake.py`). 나중에 서버를 나누게 되면
`POST /api/cs/inbound/inquiry` 를 쓰면 되고, 그때는 `.env` 의
`CS_INBOUND_SECRET` 이 필요하다. 지금은 그 값이 없어도 연동이 동작한다.

상담 만들기가 실패해도 방문자의 문의 접수는 성공한다. 이 부가 기능 때문에
본래의 문의 접수가 막히면 얻는 것보다 잃는 것이 훨씬 크기 때문이다.

## 7-4. 상담 상태·우선순위는 어디까지 바꿀 수 있나

관리자 화면(전화 설정)에서 바꿀 수 있는 것과 없는 것을 갈라 두었다.

| | 바꿀 수 있나 | 왜 |
|---|---|---|
| 화면에 보이는 이름 | O | "접수"를 "1차 확인"이라 부르고 싶을 수 있다 |
| 드롭다운 노출 여부 | O | 안 쓰는 상태를 감춰 실수를 줄인다 |
| 미처리로 셀지 | O | 보류를 미처리로 볼지는 조직마다 다르다 |
| **코드값 추가·삭제** | **X** | 엔진과 통계가 이 값을 보고 판단한다. 모르는 상태가 생기면 영영 닫히지 않는 상담이 만들어진다 |

완료(COMPLETED)는 언제나 처리된 것으로 고정한다. 이걸 미처리로 돌릴 수 있게
하면 끝난 상담이 대기 목록에 영원히 남고, 그러면 아무도 그 숫자를 안 본다.

감춘 상태로 이미 저장된 상담은 그대로 남는다. 지우는 게 아니라 가리는 것이다.

## 8. 배포

기존 배포 방식 그대로다. 새로 만든 표는 서버가 뜰 때 `create_all` 이 만든다.
기존 표의 컬럼은 하나도 건드리지 않으므로 데이터 이관이 없다.

```
1) 코드 반영
2) sudo systemctl restart udt-backend
3) sudo cp deploy/nginx-cs.conf /etc/nginx/sites-available/udjcs
   sudo nginx -t && sudo systemctl reload nginx      # WebSocket 헤더가 새로 들어갔다
4) cd frontend-cs && npm ci && npm run build          # dist 를 nginx 가 서빙한다
```

주의할 것

1. **nginx 를 반드시 다시 읽혀야 한다.** `nginx-cs.conf` 에 WebSocket 업그레이드
   설정(`map $http_upgrade $connection_upgrade` + `Upgrade`/`Connection` 헤더)을
   넣어 두었다. 이게 없으면 연결이 조용히 끊기고, 화면은 멀쩡해 보이는데
   전화만 안 뜬다. 가장 알아채기 어려운 고장이다.
   같은 `map` 블록이 다른 nginx 설정에 이미 있으면 중복 정의가 되니 하나만 남긴다.
2. `.env` 에 `PHONE_PROVIDER=mock` (기본). 실제 사업자를 붙일 때만 바꾼다.
3. `PHONE_WEBHOOK_SECRET` 없이 운영에 웹훅을 열지 않는다.
4. 실제 010 번호는 코드 어디에도 넣지 않는다. `.env` 와 DB 설정에만 둔다.
5. 통화 녹취는 인터페이스(`RecordingProvider`)만 있다. 켜기 전에 통화녹음
   고지 의무를 따로 검토한다.
6. 워커 3개(`--workers 3`) 그대로 두어도 된다. 콜 상태와 이벤트를 DB 에 두어
   워커가 갈려도 어긋나지 않게 만들었다(4장). 다만 상담원이 늘어 WebSocket
   폴링이 부담되면 `callcenter/hub.py` 의 `POLL_SECONDS` 를 올린다.

### 개발·시연

실제 전화도, 실제 DB 도 건드리지 않고 3명 순차분배를 그대로 돌려볼 수 있다.

```
backend/.venv/Scripts/python -m app.cc_demo      # 별도 데모 DB + 8000 포트
cd frontend-cs && npm run dev                    # 5175 포트
```

계정은 `cs1@demo.kr` / `cs2@demo.kr` / `cs3@demo.kr` / `admin@demo.kr`,
비밀번호는 모두 `demo1234!` 다. 창을 셋 열어 각각 로그인하고 [상담 가능] 으로
바꾼 뒤 [테스트 전화 걸기] 를 누르면 된다.

자동 검사는 이것으로 돈다.

```
cd backend && .venv/Scripts/python tests/callcenter.py
```

## 부록. 서버 인증서 자동 갱신 (2026-09-06 확인)

전화와 직접 관계는 없지만, 이 작업 중에 발견해 함께 고쳤다.

apt 로 설치된 certbot 이 pyOpenSSL 버전 충돌로 **실행 자체가 되지 않는**
상태였다(`module 'lib' has no attribute 'GEN_EMAIL'`). 자동 갱신이 멈춰
있었으므로, 그대로 뒀으면 90일 안에 udjcs·diary·udtschool·univ 네 사이트가
한꺼번에 인증서 만료로 접속 불가가 됐을 것이다.

시스템 파이썬 패키지를 손대면 다른 것이 깨질 수 있어, certbot 만
`/opt/certbot` 가상환경에 격리해 설치하고 갱신은 systemd 타이머로 돌린다.
설정은 `deploy/certbot-renew.service` 와 `.timer` 에 있다.

**nginx-cs.conf 를 서버에 덮어쓰지 말 것.** 서버 파일에는 certbot 이 넣은
HTTPS 블록이 있고, 저장소 파일로 덮으면 그것이 사라져 사이트가 다른
서버 블록으로 넘어간다. 실제로 한 번 겪었다. 파일 맨 위에 경고를 적어 두었다.
